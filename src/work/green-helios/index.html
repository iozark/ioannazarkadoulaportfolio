02 · Business Context

Why this product exists

Multi-property short-term rental hosts still manage finances across platform dashboards, invoices, and spreadsheets. As portfolios grow from one to several listings, complexity scales faster than the tools hosts use.

Green Helios addresses that gap: a specialized, finance-first product that aggregates income and expenses so hosts can evaluate portfolio performance as a business — not as disconnected booking feeds.

Timing matters: short-term rentals are operationally mature, but host tooling remains fragmented. Hosts need clarity on true profitability before they decide to keep, sell, or expand properties.

03 · The Problem

The challenge

Private hosts managing properties on Airbnb and Booking.com have no unified view of their finances. Income arrives from multiple platforms, expenses are scattered across invoices and notes, and there is no single place to understand the real profitability of each property.

Green Helios solves this — aggregating all financial activity, displaying it clearly, and helping hosts make better decisions about their portfolio.

04 · Constraints

Working inside real limits

As lead designer and developer on a team academic project, I owned both the product definition and the implementation. That dual role shaped scope: every interface had to be buildable without a dedicated QA or design-ops team.

  • Time & ownership — Design and two full implementations had to fit a fixed academic window.
  • Technology — Version 1 used Spring Boot + Thymeleaf + Bootstrap; Version 2 used Next.js + React + Tailwind. Layout flexibility differed sharply between stacks.
  • Platform — Desktop web first; mobile was out of primary scope.
  • Security baseline — Version 1 required Spring Security foundations including 2FA and role-based access, which constrained interaction patterns around auth and session handling.

06 · Research

What shaped the product

Research combined informal interviews with short-term rental hosts, competitive review of generic finance tools and property managers, and heuristic evaluation of early wireframes in Figma.

The strongest signal was not a request for richer analytics. Hosts already had data — they lacked a trustworthy answer to “am I actually making money on this property?” Spreadsheet workarounds created false confidence and delayed decisions.

Insight

Hosts asked for fewer charts and a clearer verdict — one answer before ten graphs.

07 · Success Metrics

How we would know it worked

Success was defined before build — not reverse-engineered after screenshots.

  • Business signal — Hosts with 3+ properties can evaluate keep/sell/expand decisions without rebuilding spreadsheets each month.
  • UX metric — Time to identify net profit for a selected property should drop from multi-minute spreadsheet work toward under 30 seconds in the dashboard.
  • Delivery metric — Ship a complete primary journey (auth → dashboard → properties → reports) in both architectures to prove design-to-code fidelity.

Formal A/B testing was out of scope for this project. Outcomes below are framed as delivery and qualitative signals, not invented conversion lifts.

08 · Design Strategy

Design approach

Structured product design process — starting from user needs, working through information architecture and wireframes in Figma, then progressing to high-fidelity UI and full implementation in two technical stacks.

User research → User flows → Wireframes → Visual design → Implementation

Design principles

09 · Information Architecture

Structure that supports comparison

The product is organized around a persistent sidebar: Dashboard, Profile, Properties, Reports, Notifications, Settings, and Help Center. The primary journey prioritizes portfolio health first, then property detail, then reporting.

Early exploration treated properties as isolated tabs. That pattern was rejected because hosts with multiple listings need comparison, not isolation. Filters and summary KPIs sit above detail so status stays visible while navigating.

Out of scope for v1: mobile-first layouts, automated bank imports, and marketplace booking management — the product stays finance-first.

10 · Design Decisions

Three decisions that shaped the product

Decision 1

Lead with net position, not a property showcase

Decision

Version 2 dashboard opens on KPI cards (income, expenses, balance, transactions) and charts — not a lifestyle property banner.

Alternatives considered

  • Version 1 pattern: prominent “dream home” marketing card above finances
  • Chart-first layout with KPIs buried below the fold

Trade-off

Lost decorative polish; gained immediate financial orientation aligned with host goals.

Outcome

The interface reads as a finance tool, not a listing portal — matching the problem statement.

Decision 2

Modal entry for create flows in Version 2

Decision

New property and income/expense forms use centered modals in Version 2, replacing Version 1’s right-side drawers for primary create tasks.

Alternatives considered

  • Persistent side drawers (Version 1)
  • Full-page forms that leave the list context entirely

Trade-off

Modals focus attention but hide more of the underlying list; drawers preserve context but felt heavier for short forms.

Outcome

Create tasks became shorter and more intentional; list scanning remained the default state.

Decision 3

Build the same product twice — on purpose

Decision

Implement Green Helios in Spring Boot/Thymeleaf and again in Next.js/React to learn how architecture constrains UX fidelity.

Alternatives considered

  • Ship a single stack and treat the other as mockups only
  • Design for the lowest-common-denominator (Bootstrap only)

Trade-off

Doubled implementation cost; gained concrete evidence of where design systems survive engineering constraints.

Outcome

Bootstrap limited layout precision; React enabled closer fidelity to the Figma system — a core Design Technologist lesson.

11 · Design System

Visual language for financial trust

A semantic color system built around trust and clarity. The primary teal drives interactive elements — CTAs, active states, and data visualizations. Financial status is communicated instantly through color: green for income, red for expenses, amber for warnings. Neutral backgrounds keep focus on the data.

12 · Accessibility

Accessible by default in financial UI

Accessibility was treated as a production requirement, informed by fintech work under WCAG 2.1 and by the academic focus of my studies.

  • Contrast (WCAG 1.4.3) — Body text targets 4.5:1 against white and alabaster surfaces; status colors pair with labels, not color alone.
  • Semantics — Forms use visible labels; status badges include text (Income / Expense / Warning).
  • Keyboard — Primary navigation and modal/drawer flows were designed for keyboard reachability; focus order follows sidebar → main → dialogs.
  • Error prevention — Transaction forms require property, category, amount, and date before submit to reduce silent incomplete records.

Full assistive-technology coverage across both stacks remains an ongoing hardening area — especially Bootstrap-era components in Version 1.

14 · Technical Collaboration

Built twice, on purpose

The same product was implemented in two distinct technical architectures — a deliberate decision to understand how architecture affects design flexibility, performance, and user experience.

Version 1 — Spring Boot + Thymeleaf

Server-side rendering with strong security foundations, role-based access, single-session enforcement, and JUnit 5 coverage.

Java 17 Spring Boot 3.3 Thymeleaf Bootstrap 5 PostgreSQL Spring Security 2FA Docker Railway

Version 2 — Next.js + React

Component-based architecture enabling richer interactions, a custom design system, and greater fidelity to Figma.

React Next.js TypeScript Tailwind CSS Chart.js DnD Kit Zod

Key insight

Bootstrap limited layout flexibility; React enabled pixel-closer implementation of the design system. Technical constraints directly shape UX decisions.

16 · Reflection

What I would change

I started Version 1 too attached to a visually rich dashboard — including property marketing patterns that competed with financial clarity. Building Version 2 forced a correction: start from the user’s question, not from available UI patterns in Bootstrap.

If I restarted today, I would define success metrics and the primary decision (net profit) before any high-fidelity exploration, and I would prototype create-flows as modals earlier instead of discovering the drawer-vs-modal trade-off during dual implementation.

The dual-architecture choice was expensive but instructive. It made me a better collaborator with engineering because I felt the cost of every spacing, animation, and layout choice firsthand.

17 · Next Steps

Where the product goes next

Next feature priority: seasonality-aware profitability forecasting — so hosts see not only “now” but “what is coming,” a need that emerged while defining tax-export and occupancy goals.

Before building it, I would run a focused study on how hosts currently estimate future months (spreadsheet heuristics vs. platform calendars), then prototype a single forecast strip on the dashboard rather than a separate analytics module.
